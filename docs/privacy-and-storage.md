# Local storage and data boundaries

Ley is local-first. The website may serve static HTML, CSS, JavaScript, fonts, icons, and application updates, but Ley has no knowledge-data backend.

## Storage contract

| Surface                          | Authoritative user data                                                         | Limitation                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Desktop app                      | User-selected folder containing Markdown, attachments, Canvas, and agent memory | Files depend on the user's normal device backup policy                     |
| Browser app with folder access   | User-selected folder through a permissioned directory handle                    | Browser support and renewed permission vary                                |
| Browser-local compatibility mode | IndexedDB in the current browser profile                                        | Clearing site data removes the vault; external local agents cannot open it |
| Public website                   | No knowledge data                                                               | Serves product information and static application assets only              |

Browser-local mode requests persistent browser storage when available, but ZIP backup remains necessary. Filesystem vaults are the recommended durable mode.

## Agent boundary

Ley does not independently upload notes, project scans, sessions, queries, or indexes. When a user intentionally asks a cloud agent such as Claude or Codex to retrieve Ley context, that selected context becomes visible to the agent provider as part of the agent request.

Optional meaning-based retrieval uses a pinned local Model2Vec model. Status checks, startup, ingestion, and search never download it. Only the explicit **Enable semantic search** desktop action or `ley semantic install` command contacts Hugging Face, and only for the three files at Ley's pinned model revision. Ley streams those public files into owner-private staging, checks their expected sizes and SHA-256 hashes, and atomically installs the verified model in the operating-system user cache. Project content and search queries are not included in those requests; inference remains on-device. Without a valid installation, Ley continues with lexical retrieval and discloses that fallback.

## Vault metadata

A vault-level `.ley/` directory is reserved for local Ley workspace and agent-memory files. An initialized code repository may also contain a minimal `.ley/` folder holding only its stable project identity, capture policy, and ignore rules. Repository-local metadata must not contain conversations, generated memories, credentials, embeddings, machine-specific vault paths, or raw transcripts.

The project-to-vault association lives outside both locations in Ley's private operating-system application configuration directory. Its versioned binding registry stores only stable project IDs and canonical vault paths. It contains no project path/name or knowledge content, is updated under a cross-process lock with atomic replacement, and can be deleted without deleting either project or vault data. A moved vault must be rebound explicitly; Ley does not guess another folder.

Desktop first-time setup does not create that association immediately when a folder is selected. For an uninitialized project, Ley first computes the default Structured capture plan without creating `.ley`, a binding, or private Agent Memory. The preview returns path/size metadata and policy/exclusion information only. User approval is bound to the canonical selected project root plus the exact path-free plan fingerprint; initialization rechecks that project-bound approval before writing metadata, and first ingestion rechecks the approved plan before opening the private artifact store. If later drift leaves the project initialized but unbound, first connection still requires a freshly reviewed project-bound approval. A changed candidate set therefore cannot silently broaden the first capture. See [ADR 0056](adr/0056-reviewed-first-capture-onboarding.md).

A separate owner-private device catalog remembers only initialized project roots that the user or a local Ley client explicitly opens. It stores stable project IDs, canonical project paths, and last-opened times—never names, vault paths, source, notes, sessions, or generated memory. This catalog powers the desktop Projects view without searching the device. Missing folders remain visibly unavailable, removal affects only the device list, and two simultaneously available roots cannot claim the same copied `.ley` identity. The PWA cannot read this OS-local catalog.

A separate owner-private `context-mounts-v1.json` registry records explicit project-reference authorization. Registry schema v3 stores only active/source project IDs, a stable mount ID, creation time, whether the user explicitly enabled bounded agent context, and a bounded history of historical mount-ID → source-project-ID pairs—never project paths, vault paths, source, notes, sessions, or generated memory. Legacy v1 entries default to agent-disabled and remain invisible to MCP until the user explicitly re-adds the mount; schema-v2 agent-enabled mounts are migrated into mount history before mutation. `ley mount add/list/remove` is the local user surface; adding or re-adding enables bounded read-only reference use and discloses that returned captured text may reach the connected agent/model provider. Unmount removes current read authority but retains only the stable mount/source identities so later mount-specific or source-project egress restrictions can still constrain unproven historical derivatives. Compilation revalidates current source identity/binding and reads only already-captured memory; it does not read live source or grant write authority to the mounted project.

A separate owner-private `agent-egress-v1.json` registry controls whether already-stored knowledge may enter an agent/model context. It stores only stable project/Specification/Context Mount/external-connector IDs and policy labels—never source text or project/vault paths. `agent-ok` preserves existing sharing behavior; `local-model-only` requires an MCP process explicitly launched for a local target; `never-send` is unavailable to every agent target; and `confirm-per-use` currently remains unavailable to agents until Ley has a trustworthy local confirmation flow. The registry is locked and atomically replaced, and agent operations hold its lock while enforcing policy so a local restriction change cannot race a stale in-flight policy snapshot. `ley egress` is the first local user-controlled mutation surface; MCP cannot change these policies.

Fine-grained restrictions also constrain historical agent memory conservatively. If a Specification, Context Mount, historically agent-enabled source project, or external connector is blocked for the current target, Ley does not assume that old session/decision/problem/learning text is independent of that source. Restrictive per-Specification/per-mount/per-connector overrides remain retained by stable ID even if the live authority disappears; the local user may later deliberately change or clear that retained override with `ley egress ... agent-ok`. The Context Compiler withholds unproven derivatives while the restriction remains and reports the egress ceiling, including `blockedExternalConnectors`; broad historical MCP tools fail closed under the same condition. Direct captured project artifacts, symbols, dependencies, revision metadata, graph structure, and cited evidence remain governed by the active project's own policy. This avoids laundering sensitive source text through an old summary while preserving direct project evidence that has a separately known scope.

External connector authority is separate from fetched evidence. The owner-private `external-connectors-v1.json` registry stores deterministic project/connector/provider/resource identities and no fetched body, local project/vault path, or credential. Supported public GitHub authority is limited to issue/pull-request URLs plus text-document URLs pinned to a full 40-hex commit SHA; branch/tag docs, arbitrary web URLs, private repositories, and authentication fields remain unsupported. Existing v1 issue/PR registry JSON remains readable after document fields were added. `ley connector add` is network-free. An explicit `ley connector refresh` uses a fixed-origin GitHub adapter with redirects disabled and a hard response bound: issue/PR metadata comes from generated `api.github.com` endpoints, while commit-pinned documents come from generated `raw.githubusercontent.com` endpoints and must be valid UTF-8. Core then applies the normal Ley secret redaction/control-character/field limits before storing immutable content-addressed snapshots under `<vault>/.ley/agent-memory/projects/<project-id>/external-connectors/`. Document snapshots omit issue-only state/author/labels/update/merge metadata and preserve the immutable commit/path in their source identity. Those snapshots are covered by whole-project Agent Memory erasure. Removing one connector deletes its connector snapshot directory and authority, while a restrictive egress override remains outside the erasable snapshot namespace until explicitly changed. MCP list/get read stored state only and never refresh GitHub.

Cross-project memory search reads that bounded catalog without adding entries. Each root must still present its recorded project identity and resolve its own available binding before Ley searches the corresponding captured vault namespace. Unavailable scopes are skipped, no neighboring folders are scanned, and searching does not ingest current source. Results can therefore be older than the working tree and retain captured-snapshot citations.

After an explicit ingestion command, deterministic project evidence lives under `<vault>/.ley/agent-memory/projects/<project-id>/`. Structured and Full Evidence modes retain allowed UTF-8 source text only after local credential redaction; Minimal mode retains artifact metadata and post-redaction hashes without source blobs. Full Evidence additionally retains supported PNG/JPEG/WebP original image evidence after extension/signature validation. Structured/Minimal do not retain those pixels and report `media-requires-full-evidence`. Other binary/non-UTF-8 files, ignored paths, and detected raw text values are not copied. Text redaction is a safety layer, not a guarantee that every possible secret is recognizable, and Ley does not visually redact image pixels, so preview and project-specific ignore rules remain important.

The durable agent project graph is derived locally from that same post-redaction boundary. It stores project-relative file/symbol citations, syntax-level imports/calls/inheritance, declared dependencies, and bounded tracked Git state. An unambiguous relative JavaScript/TypeScript import or explicit Python relative import may resolve to another file only by comparing the module target with the already-approved captured path set; Ley does not probe the live filesystem, infer Python package roots, or resolve absolute Python/package imports, and ambiguous/escaping targets remain external. Git cannot introduce untracked or excluded paths. The graph stores no project root or vault path and does not run compilers, build scripts, package managers, language servers, or models. A bounded private history index references retained immutable graph/artifact pairs. Historical source inspection reads only an exact citation belonging to the selected graph, from that graph's matching redacted artifact; it never falls through to the live project. Minimal captures retain the relationship and citation metadata but no inspectable source text.

Structured session events live under `<vault>/.ley/agent-memory/projects/<project-id>/sessions/`. They contain bounded summaries, decisions, tasks, problem outcomes, commands, verification, handoffs, citations, and separate prompt/response observations that the user or an approved adapter submits. Structured and Full Evidence retain bounded pattern-redacted turn bodies; Minimal retains body-free disclosure events. Ley does not read or capture a raw transcript automatically. Users and adapters must still avoid environment dumps, complete tool logs, and unrelated private text. Derived JSON and Markdown views can be rebuilt from the event sequence.

Explicit historical host import uses that same private session ledger rather than a second transcript database. The first supported source is a user-supplied Codex global message-history JSONL file plus one explicitly selected session UUID. Ley opens only that explicit regular file with no-follow semantics, validates the documented `session_id` / Unix-second `ts` / `text` record shape, and bounds the read to 64 MiB, 100,000 records, 1 MiB per record, and 512 selected messages. Only selected user messages are imported. The external file path, raw Codex session UUID, assistant/tool/hidden-reasoning history, and unrelated-session messages are not retained. The session stores an opaque `hsi_` source reference and each imported turn stores its original source timestamp. Existing capture mode and secret-redaction rules apply before durable bodies are written. The import does not scan `~/.codex`, parse rollout/session transcripts, or add an MCP import route.

Imported history is deliberately not treated as newly current simply because the import happened now. Imported sessions are excluded from automatic Resume; project-memory search uses the latest imported source timestamp for the session's temporal signal; and Memory Health does not classify intentionally imported raw history as a missed-checkpoint backlog. Explicit inspection and Memory Compiler access remain available. Exact retries replay the same immutable Ley import; a changed selected-message snapshot creates a new Ley session with the same opaque source identity. Deleting the external source later does not change the retained snapshot, and ordinary session erasure removes Ley's private imported-session copy without claiming to delete the external Codex file.

Desktop Capture & privacy controls change repository-evidence retention without changing the approved root implicitly. Minimal current snapshots omit source blobs; Structured retains post-redaction UTF-8 source; Full Evidence retains that source plus supported original image evidence and explicitly permits a compatible adapter to submit raw host evidence. Full Evidence requires a separate acknowledgement and still does not cause Ley to scrape transcripts. Mode changes preserve custom roots, ignore behavior, and byte limits, then refresh the bound local snapshot. Switching to Minimal is not secure deletion of earlier snapshots.

The separate exact-name **Erase Agent Memory** action removes the entire per-project memory namespace—artifacts and history, graph, sessions, and lessons—from the bound vault. It preserves project files, ordinary vault notes/Canvases, `.ley` metadata, the private binding, and the observation entry so the user can recapture deliberately. A sibling lifecycle lock serializes erasure against current-version memory readers and writers. This is logical local deletion, not a forensic wipe of backups, filesystem snapshots, SSD remnants, or external copies.

Evidence-backed project lessons live under the sibling `learnings/` directory. Their immutable events contain bounded claims, actor/provenance, confidence, references to existing session records, corrections, review feedback, and, for current schema-v2 proposals/corrections, bounded origin lineage. That provenance metadata may retain stable session record IDs, project-relative captured artifact paths, artifact snapshot IDs and content hashes, a bound recovery candidate fingerprint, and exact `tev_` turn-evidence IDs. It stores no absolute project or vault path, and it does not duplicate complete source/turn text merely because the origin was cited. Legacy v1 events remain readable but cannot be retroactively presented as fully mechanically resolved lineage.

Agent proposals are not trusted automatically. Automatic derivation has a `review-required` authority ceiling; only an explicit user confirmation can establish trusted learning state. Human trust does not erase the stored origin history or prove that the mechanically recorded origins capture every causal influence on the derived claim. Source changes remain visible through citation-hash freshness. Recognized credentials are redacted before persistence, but the same redaction limitations apply. Derived JSON and Markdown review views can be rebuilt from the event ledger.

Topic Dossiers add no new durable store in the current P1 slice. `ley_topic_dossier` rebuilds a bounded topic projection on demand from already-captured project evidence and retained structured memory, then returns it without writing a dossier file or cache. Stable evidence IDs, captured artifact citations/hashes, supporting-session IDs, revision applicability, open work, verification, conflicts, and a SHA-256 source fingerprint may be returned to the caller, but absolute project/vault paths are not. The dossier remains subject to the same historical-memory egress ceiling as broad session/learning readers. Because nothing is persisted, session/project erasure requires no separate dossier purge transaction today; the deletion-fidelity eval explicitly rebuilds a dossier after erasure and requires erased canaries to remain unrecoverable. Any future persisted/background dossier tier must add dependency-aware invalidation and erasure before it can ship.

Current Project State also adds no durable store. `ley_project_state` rebuilds project status on demand from already-retained structured sessions, learning state, captured snapshot identity, and bounded Git freshness metadata. Returned text is aggregate-character-budgeted and may include active/paused latest-checkpoint state, recent historical decisions/verification, trusted-current reviewed knowledge, and attention-needed learning state. The response carries only stable IDs and structured state; it does not expose project/vault paths and keeps `liveSourceChecked: false`. The same historical-memory egress ceiling applies. Because there is no persisted state cache, session/project erasure needs no additional state purge transaction; deletion-fidelity evaluation calls `ley_project_state` after erasure and requires erased canaries to remain absent.

Context Pack Inspector also persists nothing. `ley_compile_context` returns a logical `contextPackId` and creation time for the supplied pack. `ley_context_pack_inspect` recompiles through the same egress-aware compiler path and returns only diagnostic metadata, not another copy of included source/specification/excerpt text. Stable IDs, project-relative citations/paths, hashes, authority/admission reasons, policy scope IDs, exclusions, conflicts, retrieval/revision metadata, budget composition, coverage, and follow-up handles may be exposed. Absolute project/vault paths are not returned. A mismatched expected pack ID is disclosed rather than silently reconstructing stale context. Any future persisted pack-history feature must define retention, deletion, egress inheritance, and storage bounds explicitly.

Context/memory utility feedback deliberately does persist a small amount of metadata, but only inside the existing private structured-session ledger. `ley_context_utility_bind` stores the exact logical `contextPackId`, a redacted bounded task excerpt, snapshot IDs, egress target when present, compiler result/token limits and estimate, and at most 64 stable included-record handles with an omission count; active-project learning handles may additionally carry the learning kind and exact ledger event count supplied in that pack. It does not store compiled Specification/source/memory/mounted-reference bodies or reconstruct the original compile timestamp. `ley_context_utility_observe` stores the binding ID, cited same-session checkpoint/session-finish event IDs, deterministically derived typed outcome counts, and—only when explicitly supplied—a bounded list of caller-declared applied Procedure learning IDs that must resolve to exact versions in that binding. Claim-bearing observations use session schema v15; ordinary utility events remain v5. `ley_learning_get` rebuilds a bounded reverse application history from those existing session ledgers and persists no second copy. There is no separate utility analytics database, telemetry upload, reward log, or automatic ranking/trust state. `ley_session_get` returns at most five recent observations and at most 24 included-record handles per observation, disclosing omissions. Session/project erasure removes the utility binding/observation with the same ledger; there is no second feedback store to purge. Agent-facing reads remain behind the existing historical-memory egress boundary and omit absolute project/vault paths.

Memory Health adds no durable store and performs no cleanup mutation. `ley_memory_health` rebuilds advisory hygiene signals from the fixed project's retained learning summaries, structured sessions, Memory Compiler metadata, snapshot identity, and bounded Git freshness metadata. It may expose learning/session/checkpoint stable IDs plus bounded titles/details and typed severity/recommended actions, but it does not expose project/vault paths. Schema-v2 Procedure outcome attention additionally exposes only the exact learning/session/observation IDs and typed verification counts already retained in a selected session; it copies no Procedure guidance, task excerpt, context body, or prompt/response body. Post-checkpoint recovery health likewise returns counts/state rather than captured prompt/response bodies. The report is subject to the same historical-memory egress ceiling as broad historical readers, keeps `liveSourceChecked: false`, reports `destructiveActionsTaken: false`, and persists no health cache. Deletion-fidelity evaluation rebuilds the health report after erasure and requires erased canaries to remain absent.

Agent Legibility adds no durable store. `ley_agent_legibility` rebuilds a bounded project-orientation table of contents from captured artifact/graph metadata, retained structured checkpoint command/plan metadata, and current approved Specification registry metadata. Returned paths are project-relative; stable IDs, hashes, snapshot IDs, and bounded copied command/plan text may be returned, but source excerpts, Specification bodies, prompt/response bodies, absolute project paths, and absolute vault paths are not. Minimal capture does not fall back to live source when a captured `package.json` body is unavailable; declared commands remain absent and the map reports a gap instead of inventing defaults. The projection remains subject to the historical-memory egress ceiling, keeps `liveSourceChecked: false`, and persists no cache. Session/project erasure therefore requires no separate legibility purge transaction; rebuilding after erasure must not recover erased session-derived plans or observed commands.

Reviewed Runbooks and host Skill export add no durable store in this P1 slice. `ley runbook compile` reads only explicitly selected same-project learnings that are verified, trusted, current, and typed as procedures, pitfalls, or conventions, then returns a bounded source-bound Markdown projection. The output can include selected learning titles/guidance plus stable learning IDs, provenance, confidence/freshness, event counts, and hashes; it does not copy learning evidence notes, unrelated session state, prompt/response bodies, or absolute project/vault paths. `ley runbook export-skill` requires an exact reviewed runbook ID and explicit host/egress target, rechecks historical-memory egress, and returns Skill content with `persisted: false` and `installed: false`; it does not create `SKILL.md` or mutate a host configuration. A changed learning/source state invalidates the reviewed ID instead of silently exporting stale content. Because neither projection nor export is stored by Ley, later learning/session/project erasure requires no separate runbook/Skill cache purge; a subsequent compile/export is rebuilt from then-current retained authority.

Verification evidence links reuse the existing structured-session ledger and captured-artifact store rather than creating a new runtime-log database. A verification may name bounded project-relative `evidenceArtifactPaths`; Ley resolves them only against the current approved captured manifest. Text evidence persists immutable path/snapshot/hash/line citations in schema-v4 checkpoints. Under explicit Full Evidence capture, a supported image path persists the same immutable path/snapshot/hash identity plus `mediaType` with a deliberate non-text `0/0` range in schema-v6 checkpoints. Ley does not read an uncaptured live file, follow arbitrary external references, copy the cited body into the verification record, or generate OCR/vision text. A later live-file change does not mutate the stored hash and does not make `liveSourceChecked` true.

The direct media reader resolves exact retained path/snapshot/hash provenance only. Local core/desktop delivery is capped at 1 MiB per requested image; agent-facing `ley_read_media_evidence` uses the active-project egress gate, returns a native MCP image block plus compact provenance, caps source bytes at 180,000 so the complete serialized result remains under Ley's 256 KiB MCP limit, and exposes no absolute project/vault path. The original image remains `untrusted-project-evidence`; a model's later interpretation is derived and is not stored or silently promoted by this slice. CI-provider attachments, PDFs/OCR pipelines, audio/video, arbitrary binary attachments, and provider/runtime screenshot collection still require separate designs. See [ADR 0051](adr/0051-bounded-original-image-evidence.md).

Branch/worktree visibility and revision-scoped search add no durable store or branch-specific Ley project. Applicability is rebuilt from already-stored checkpoint/capture revision IDs plus bounded local Git metadata/ancestry at read time, so a retained checkpoint can become `merged` after Git history changes without rewriting memory or re-ingesting source. The freshness beacon returns bounded HEAD/branch/tracked-change counts and compatibility; it does not return live status paths, arbitrary worktree paths, or file contents, and `liveSourceChecked` remains false. An exact Memory Search revision filter only narrows the returned fixed-project candidate set and creates no additional copy. `revisionFilteredCandidates` reports the deliberate omission count, while default unfiltered search preserves the prior all-history behavior.

User-approved Specifications remain ordinary Markdown notes in the bound vault rather than being copied into Agent Memory. The private OS-local `specifications-v1.json` authority registry stores only project ID, stable Specification ID, vault-relative Markdown path, exact SHA-256 source hash, and approval time. Editing, moving away from the pinned path, or deleting the note prevents that approval from returning requirement text until the user deliberately approves the current revision again. Revocation deletes only the authority record; the user's note remains. **Erase Agent Memory** does not remove Specification notes or this human-authority registry.

Bootstrap authority is separate from both target project memory and ordinary per-project Specification/Context Mount authority. The owner-private `bootstrap-specifications-v1.json` registry is schema v2 and lets the local user grant one still-uninitialized workspace either exact **already-approved** source Specifications (`bsg_`) or lower-authority captured reference projects (`brg_`). It stores the target's canonical local path and, on supported Unix filesystems, a generation made from device/inode plus filesystem creation time. Specification grants additionally store stable Specification ID plus exact approved source hash; reference grants store only stable source project ID and attachment time. The registry stores no Specification or reference body, and agent-facing output never returns canonical target/source/vault paths. At read time source identity and current binding are revalidated. Specification delivery checks source-project plus exact source-Specification egress before opening the approved note. Reference delivery checks source-project egress before searching only already-captured Ley memory, then verifies the expected source project identity around the search; a source pathname replacement therefore cannot substitute another project's memory. Bounded live Git metadata may be inspected only as a freshness beacon, never as live source content. Bootstrap reads do not scan/capture the target, create `.ley`, start a session, retain prompt/response text, or create target project memory. Attach, compile, and public initialization serialize through the same non-persistent target transition; successful initialization retires the whole Specification/reference record permanently. See [ADR 0058](adr/0058-bootstrap-specifications-for-uninitialized-workspaces.md) and [ADR 0059](adr/0059-bootstrap-reference-projects-for-uninitialized-workspaces.md).

Creating an ordinary note from a trusted lesson or inspected session is a separate explicit desktop action. Because the Projects catalog can open memory bound to another vault, Ley resolves the private binding and canonically compares it with the currently open note vault before every link. A mismatch fails without writing and exposes only folder names, not absolute paths. Created notes are user-owned attributed snapshots; they do not replace, rewrite, or silently synchronize the immutable memory ledger.

`ley mcp` is a local stdio child process, not a network service. The normal ready process is fixed to one explicitly initialized project and its resolved vault binding. The explicit Bootstrap Context server is a separate narrow mode for an uninitialized target and exposes only `ley_compile_context` with no resources or target project-memory/session tools. The default egress target is `cloud`; `--egress-target local` is an explicit integration assertion and is not automatic proof that the downstream model/runtime is physically local. Every normal agent-facing tool/resource operation rechecks the active project's private egress policy; bootstrap Specification delivery checks source-project plus exact source-Specification policy, while Bootstrap Reference delivery checks the explicit source project's project policy before searching captured memory. Reference-only bootstrap authority does not enable automatic host-hook context. `ley_project_specifications` checks a Specification override before opening its note, external connector list/get check the exact connector override before returning metadata/snapshot content, and the normal Context Compiler checks Specification/mount/source-project/shared-scope-source/policy-bundle-source/connector egress before those sources or unproven derivatives can participate in agent context. Reusable `team`/`organization` Knowledge Scope authority lives in owner-private `knowledge-scopes-v1.json` as stable IDs, names/kinds, immutable source project IDs, explicit attachments, and bounded historical source ancestry only; it stores no project/vault path and MCP has no scope-mutation route. Reusable Policy Bundle authority lives separately in owner-private `policy-bundles-v1.json`; it stores stable bundle/scope/project/Specification IDs, exact approved content hashes, explicit attachments, and bounded historical ancestry, but no policy body or project/vault path. A bundle source must already belong to its parent scope, and that scope must be attached before the bundle can be attached. Detaching a scope or Policy Bundle removes current access/authority but does not erase the retained ancestry needed to keep later source-project/source-Specification restrictions from laundering old derivatives. Read paths may additionally run a bounded local Git metadata check as a non-ingesting revision-freshness beacon. No egress check changes `liveSourceChecked: false`. The MCP process itself performs no connector network refresh; only the separate explicit local `ley connector refresh` command contacts GitHub. When a globally installed host package starts Ley in an ordinary, unavailable, or project-policy-blocked workspace, the CLI keeps a protocol-valid zero-capability connection rather than returning knowledge; only current explicit Bootstrap Specification/reference authority enables the one-tool exception. Ley makes no independent background/cloud knowledge upload; after allowed content is returned to a host, that host/provider controls its downstream transport and retention.

The optional `--allow-session-writes` launch flag adds append-only start, checkpoint, finish, and candidate-bound unresolved-recovery commit tools for that process. The independent `--allow-learning-proposals` flag adds one agent-only, review-required proposal route. Neither enables deletion or raw transcript capture, and the proposal flag grants no review authority. Writes stay inside the bound filesystem vault and use the same local redaction and citation rules as the CLI. The host controls its own per-call approval interface.

Ordinary note search and visualization indexes remain disposable local database state. The versioned agent graph is a rebuildable but intentionally durable cited projection so agents can inspect immutable historical snapshots; deleting it must never delete source artifacts or the authoritative filesystem vault.

## Required safeguards

- Self-host runtime fonts, scripts, icons, and application assets.
- No hidden analytics, telemetry, remote database, or mandatory account.
- Constrain filesystem operations and project ingestion to explicitly approved roots.
- Exclude credentials, private keys, environment secrets, VCS internals, build output, and configured ignore patterns by default.
- Treat retrieved project or session text as untrusted evidence rather than executable agent instructions.
- Preserve citations, provenance, corrections, and superseded facts.
- Keep browser-local ZIP import/export and disclose its durability limitations.
