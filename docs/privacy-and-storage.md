# Local storage and data boundaries

Ley is local-first. The website may serve static HTML, CSS, JavaScript, fonts, icons, and application updates, but Ley has no knowledge-data backend.

## Storage contract

| Surface                          | Authoritative user data                                                         | Limitation                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Desktop app                      | User-selected folder containing Markdown, attachments, Canvas, and agent memory | Files depend on the user's normal device backup policy                     |
| Browser app with folder access   | User-selected folder through a permissioned directory handle                    | Browser support and renewed permission vary                                |
| Browser-local compatibility mode | IndexedDB in the current browser profile                                        | Clearing site data removes the vault; external local agents cannot open it |
| Public website                   | No knowledge data                                                               | Serves product information and static application assets only              |

Browser-local mode requests persistent browser storage when available, but ZIP backup remains necessary. Filesystem vaults are the recommended durable mode.

## Agent boundary

Ley does not independently upload notes, project scans, sessions, queries, or indexes. When a user intentionally asks a cloud agent such as Claude or Codex to retrieve Ley context, that selected context becomes visible to the agent provider as part of the agent request.

Optional meaning-based retrieval uses a pinned local Model2Vec model. Status checks, startup, ingestion, and search never download it. Only the explicit **Enable semantic search** desktop action or `ley semantic install` command contacts Hugging Face, and only for the three files at Ley's pinned model revision. Ley streams those public files into owner-private staging, checks their expected sizes and SHA-256 hashes, and atomically installs the verified model in the operating-system user cache. Project content and search queries are not included in those requests; inference remains on-device. Without a valid installation, Ley continues with lexical retrieval and discloses that fallback.

## Vault metadata

A vault-level `.ley/` directory is reserved for local Ley workspace and agent-memory files. An initialized code repository may also contain a minimal `.ley/` folder holding only its stable project identity, capture policy, and ignore rules. Repository-local metadata must not contain conversations, generated memories, credentials, embeddings, machine-specific vault paths, or raw transcripts.

The project-to-vault association lives outside both locations in Ley's private operating-system application configuration directory. Its versioned binding registry stores only stable project IDs and canonical vault paths. It contains no project path/name or knowledge content, is updated under a cross-process lock with atomic replacement, and can be deleted without deleting either project or vault data. A moved vault must be rebound explicitly; Ley does not guess another folder.

A separate owner-private device catalog remembers only initialized project roots that the user or a local Ley client explicitly opens. It stores stable project IDs, canonical project paths, and last-opened times—never names, vault paths, source, notes, sessions, or generated memory. This catalog powers the desktop Projects view without searching the device. Missing folders remain visibly unavailable, removal affects only the device list, and two simultaneously available roots cannot claim the same copied `.ley` identity. The PWA cannot read this OS-local catalog.

A separate owner-private `context-mounts-v1.json` registry records explicit project-reference authorization. Registry schema v3 stores only active/source project IDs, a stable mount ID, creation time, whether the user explicitly enabled bounded agent context, and a bounded history of historical mount-ID → source-project-ID pairs—never project paths, vault paths, source, notes, sessions, or generated memory. Legacy v1 entries default to agent-disabled and remain invisible to MCP until the user explicitly re-adds the mount; schema-v2 agent-enabled mounts are migrated into mount history before mutation. `ley mount add/list/remove` is the local user surface; adding or re-adding enables bounded read-only reference use and discloses that returned captured text may reach the connected agent/model provider. Unmount removes current read authority but retains only the stable mount/source identities so later mount-specific or source-project egress restrictions can still constrain unproven historical derivatives. Compilation revalidates current source identity/binding and reads only already-captured memory; it does not read live source or grant write authority to the mounted project.

A separate owner-private `agent-egress-v1.json` registry controls whether already-stored knowledge may enter an agent/model context. It stores only stable project/Specification/Context Mount IDs and policy labels—never source text or project/vault paths. `agent-ok` preserves existing sharing behavior; `local-model-only` requires an MCP process explicitly launched for a local target; `never-send` is unavailable to every agent target; and `confirm-per-use` currently remains unavailable to agents until Ley has a trustworthy local confirmation flow. The registry is locked and atomically replaced, and agent operations hold its lock while enforcing policy so a local restriction change cannot race a stale in-flight policy snapshot. `ley egress` is the first local user-controlled mutation surface; MCP cannot change these policies.

Fine-grained restrictions also constrain historical agent memory conservatively. If a Specification, Context Mount, or historically agent-enabled source project is blocked for the current target, Ley does not assume that old session/decision/problem/learning text is independent of that source. Restrictive per-Specification/per-mount overrides remain retained by stable ID even if the live authority disappears; the local user may later deliberately change or clear that retained override with `ley egress ... agent-ok`. The Context Compiler withholds unproven derivatives while the restriction remains and reports the egress ceiling; broad historical MCP tools fail closed under the same condition. Direct captured project artifacts, symbols, dependencies, revision metadata, graph structure, and cited evidence remain governed by the active project's own policy. This avoids laundering sensitive source text through an old summary while preserving direct project evidence that has a separately known scope.

Cross-project memory search reads that bounded catalog without adding entries. Each root must still present its recorded project identity and resolve its own available binding before Ley searches the corresponding captured vault namespace. Unavailable scopes are skipped, no neighboring folders are scanned, and searching does not ingest current source. Results can therefore be older than the working tree and retain captured-snapshot citations.

After an explicit ingestion command, deterministic project evidence lives under `<vault>/.ley/agent-memory/projects/<project-id>/`. Structured and Full Evidence modes retain allowed UTF-8 source text only after local credential redaction; Minimal mode retains artifact metadata and post-redaction hashes without source blobs. Binary/non-UTF-8 files, ignored paths, and detected raw values are not copied. Redaction is a safety layer, not a guarantee that every possible secret is recognizable, so preview and project-specific ignore rules remain important.

The durable agent project graph is derived locally from that same post-redaction boundary. It stores project-relative file/symbol citations, syntax-level imports/calls/inheritance, declared dependencies, and bounded tracked Git state. Git cannot introduce untracked or excluded paths. It stores no project root or vault path and does not run compilers, build scripts, package managers, language servers, or models. A bounded private history index references retained immutable graph/artifact pairs. Historical source inspection reads only an exact citation belonging to the selected graph, from that graph's matching redacted artifact; it never falls through to the live project. Minimal captures retain the relationship and citation metadata but no inspectable source text.

Structured session events live under `<vault>/.ley/agent-memory/projects/<project-id>/sessions/`. They contain bounded summaries, decisions, tasks, problem outcomes, commands, verification, handoffs, citations, and separate prompt/response observations that the user or an approved adapter submits. Structured and Full Evidence retain bounded pattern-redacted turn bodies; Minimal retains body-free disclosure events. Ley does not read or capture a raw transcript automatically. Users and adapters must still avoid environment dumps, complete tool logs, and unrelated private text. Derived JSON and Markdown views can be rebuilt from the event sequence.

Desktop Capture & privacy controls change repository-evidence retention without changing the approved root implicitly. Minimal current snapshots omit source blobs; Structured retains post-redaction source; Full Evidence retains the same source and explicitly permits a compatible adapter to submit raw host evidence. Full Evidence requires a separate acknowledgement and still does not cause Ley to scrape transcripts. Mode changes preserve custom roots, ignore behavior, and byte limits, then refresh the bound local snapshot. Switching to Minimal is not secure deletion of earlier snapshots.

The separate exact-name **Erase Agent Memory** action removes the entire per-project memory namespace—artifacts and history, graph, sessions, and lessons—from the bound vault. It preserves project files, ordinary vault notes/Canvases, `.ley` metadata, the private binding, and the observation entry so the user can recapture deliberately. A sibling lifecycle lock serializes erasure against current-version memory readers and writers. This is logical local deletion, not a forensic wipe of backups, filesystem snapshots, SSD remnants, or external copies.

Evidence-backed project lessons live under the sibling `learnings/` directory. Their immutable events contain bounded claims, actor/provenance, confidence, references to existing session records, corrections, review feedback, and, for current schema-v2 proposals/corrections, bounded origin lineage. That provenance metadata may retain stable session record IDs, project-relative captured artifact paths, artifact snapshot IDs and content hashes, a bound recovery candidate fingerprint, and exact `tev_` turn-evidence IDs. It stores no absolute project or vault path, and it does not duplicate complete source/turn text merely because the origin was cited. Legacy v1 events remain readable but cannot be retroactively presented as fully mechanically resolved lineage.

Agent proposals are not trusted automatically. Automatic derivation has a `review-required` authority ceiling; only an explicit user confirmation can establish trusted learning state. Human trust does not erase the stored origin history or prove that the mechanically recorded origins capture every causal influence on the derived claim. Source changes remain visible through citation-hash freshness. Recognized credentials are redacted before persistence, but the same redaction limitations apply. Derived JSON and Markdown review views can be rebuilt from the event ledger.

Topic Dossiers add no new durable store in the current P1 slice. `ley_topic_dossier` rebuilds a bounded topic projection on demand from already-captured project evidence and retained structured memory, then returns it without writing a dossier file or cache. Stable evidence IDs, captured artifact citations/hashes, supporting-session IDs, revision applicability, open work, verification, conflicts, and a SHA-256 source fingerprint may be returned to the caller, but absolute project/vault paths are not. The dossier remains subject to the same historical-memory egress ceiling as broad session/learning readers. Because nothing is persisted, session/project erasure requires no separate dossier purge transaction today; the deletion-fidelity eval explicitly rebuilds a dossier after erasure and requires erased canaries to remain unrecoverable. Any future persisted/background dossier tier must add dependency-aware invalidation and erasure before it can ship.

Current Project State also adds no durable store. `ley_project_state` rebuilds project status on demand from already-retained structured sessions, learning state, captured snapshot identity, and bounded Git freshness metadata. Returned text is aggregate-character-budgeted and may include active/paused latest-checkpoint state, recent historical decisions/verification, trusted-current reviewed knowledge, and attention-needed learning state. The response carries only stable IDs and structured state; it does not expose project/vault paths and keeps `liveSourceChecked: false`. The same historical-memory egress ceiling applies. Because there is no persisted state cache, session/project erasure needs no additional state purge transaction; deletion-fidelity evaluation calls `ley_project_state` after erasure and requires erased canaries to remain absent.

Context Pack Inspector also persists nothing. `ley_compile_context` returns a logical `contextPackId` and creation time for the supplied pack. `ley_context_pack_inspect` recompiles through the same egress-aware compiler path and returns only diagnostic metadata, not another copy of included source/specification/excerpt text. Stable IDs, project-relative citations/paths, hashes, authority/admission reasons, policy scope IDs, exclusions, conflicts, retrieval/revision metadata, budget composition, coverage, and follow-up handles may be exposed. Absolute project/vault paths are not returned. A mismatched expected pack ID is disclosed rather than silently reconstructing stale context. Any future persisted pack-history feature must define retention, deletion, egress inheritance, and storage bounds explicitly.

Memory Health adds no durable store and performs no cleanup mutation. `ley_memory_health` rebuilds advisory hygiene signals from the fixed project's retained learning summaries, structured sessions, Memory Compiler metadata, snapshot identity, and bounded Git freshness metadata. It may expose learning/session/checkpoint stable IDs plus bounded titles/details and typed severity/recommended actions, but it does not expose project/vault paths. Post-checkpoint recovery health returns counts/state rather than captured prompt/response bodies. The report is subject to the same historical-memory egress ceiling as broad historical readers, keeps `liveSourceChecked: false`, reports `destructiveActionsTaken: false`, and persists no health cache. Deletion-fidelity evaluation rebuilds the health report after erasure and requires erased canaries to remain absent.

Agent Legibility adds no durable store. `ley_agent_legibility` rebuilds a bounded project-orientation table of contents from captured artifact/graph metadata, retained structured checkpoint command/plan metadata, and current approved Specification registry metadata. Returned paths are project-relative; stable IDs, hashes, snapshot IDs, and bounded copied command/plan text may be returned, but source excerpts, Specification bodies, prompt/response bodies, absolute project paths, and absolute vault paths are not. Minimal capture does not fall back to live source when a captured `package.json` body is unavailable; declared commands remain absent and the map reports a gap instead of inventing defaults. The projection remains subject to the historical-memory egress ceiling, keeps `liveSourceChecked: false`, and persists no cache. Session/project erasure therefore requires no separate legibility purge transaction; rebuilding after erasure must not recover erased session-derived plans or observed commands.

Reviewed Runbooks and host Skill export add no durable store in this P1 slice. `ley runbook compile` reads only explicitly selected same-project learnings that are verified, trusted, current, and typed as procedures, pitfalls, or conventions, then returns a bounded source-bound Markdown projection. The output can include selected learning titles/guidance plus stable learning IDs, provenance, confidence/freshness, event counts, and hashes; it does not copy learning evidence notes, unrelated session state, prompt/response bodies, or absolute project/vault paths. `ley runbook export-skill` requires an exact reviewed runbook ID and explicit host/egress target, rechecks historical-memory egress, and returns Skill content with `persisted: false` and `installed: false`; it does not create `SKILL.md` or mutate a host configuration. A changed learning/source state invalidates the reviewed ID instead of silently exporting stale content. Because neither projection nor export is stored by Ley, later learning/session/project erasure requires no separate runbook/Skill cache purge; a subsequent compile/export is rebuilt from then-current retained authority.

User-approved Specifications remain ordinary Markdown notes in the bound vault rather than being copied into Agent Memory. The private OS-local `specifications-v1.json` authority registry stores only project ID, stable Specification ID, vault-relative Markdown path, exact SHA-256 source hash, and approval time. Editing, moving away from the pinned path, or deleting the note prevents that approval from returning requirement text until the user deliberately approves the current revision again. Revocation deletes only the authority record; the user's note remains. **Erase Agent Memory** does not remove Specification notes or this human-authority registry.

Creating an ordinary note from a trusted lesson or inspected session is a separate explicit desktop action. Because the Projects catalog can open memory bound to another vault, Ley resolves the private binding and canonically compares it with the currently open note vault before every link. A mismatch fails without writing and exposes only folder names, not absolute paths. Created notes are user-owned attributed snapshots; they do not replace, rewrite, or silently synchronize the immutable memory ledger.

`ley mcp` is a local stdio child process, not a network service. A ready process is fixed to one explicitly initialized project and its resolved vault binding. The default egress target is `cloud`; `--egress-target local` is an explicit integration assertion and is not automatic proof that the downstream model/runtime is physically local. Every agent-facing tool/resource operation rechecks the active project's private egress policy. `ley_project_specifications` checks a Specification override before opening its note, and the Context Compiler checks Specification/mount/source-project egress before those sources can participate in retrieval or derivative assembly. Read paths may additionally run a bounded local Git metadata check as a non-ingesting revision-freshness beacon. No egress check changes `liveSourceChecked: false`. When a globally installed host package starts Ley in an ordinary, unavailable, or project-policy-blocked workspace, the CLI keeps a protocol-valid zero-capability connection rather than returning knowledge. Ley itself makes no independent cloud upload; after allowed content is returned to a host, that host/provider controls its downstream transport and retention.

The optional `--allow-session-writes` launch flag adds append-only start, checkpoint, finish, and candidate-bound unresolved-recovery commit tools for that process. The independent `--allow-learning-proposals` flag adds one agent-only, review-required proposal route. Neither enables deletion or raw transcript capture, and the proposal flag grants no review authority. Writes stay inside the bound filesystem vault and use the same local redaction and citation rules as the CLI. The host controls its own per-call approval interface.

Ordinary note search and visualization indexes remain disposable local database state. The versioned agent graph is a rebuildable but intentionally durable cited projection so agents can inspect immutable historical snapshots; deleting it must never delete source artifacts or the authoritative filesystem vault.

## Required safeguards

- Self-host runtime fonts, scripts, icons, and application assets.
- No hidden analytics, telemetry, remote database, or mandatory account.
- Constrain filesystem operations and project ingestion to explicitly approved roots.
- Exclude credentials, private keys, environment secrets, VCS internals, build output, and configured ignore patterns by default.
- Treat retrieved project or session text as untrusted evidence rather than executable agent instructions.
- Preserve citations, provenance, corrections, and superseded facts.
- Keep browser-local ZIP import/export and disclose its durability limitations.
